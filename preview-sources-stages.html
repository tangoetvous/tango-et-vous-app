S1/S1b/S2 — Mécanique couple (emails distincts vs partagés)

hasPartEmail : hasPartner && partEmail non vide && partEmail !== email && !emailPartage → envoie un email séparé au partenaire
Boucle recipients : Tableau de 1 ou 2 entrées selon hasPartEmail. Chaque entrée = { to, pren, nom, role, myDates, theirDates, theirPren, theirNom, theirRole }
buildEleveStagesBlock() : Helper worker — si partenaire a des stages (theirDates.length > 0) → deux sections labellisées (fond beige pour "Vos stages", fond violet pour "Stages de votre partenaire"). Sinon → stage-box simple.
Email partagé : si emailPartage=true → 1 seul email, sections Thomas + Marie côte à côte (même comportement que S1d)
Partenaire sans email : si partEmail vide → seul l'inscripteur reçoit l'email, avec les deux sections (ses stages + stages partenaire)

Action élève via email — confirmer présence stage (RPC SECURITY DEFINER)

Route worker : GET /api/stages/confirmer?email=&date=&token= → handleStagesConfirmer
Token HMAC : HMAC-SHA256(${email}:${date}, SUPABASE_ANON).slice(0,32) (pas d'id — plusieurs lignes possibles par couple email+date)
Backend : RPC Supabase confirmer_stage(p_email, p_date, p_token, p_secret) — SECURITY DEFINER, bypass RLS, vérifie HMAC server-side, UPDATE presence_confirmee=true sur toutes les lignes inscriptions_stages WHERE email=p_email AND stage_date=p_date
Réponse : page verte 👍 "Présence confirmée !" si result.updated > 0, sinon "Déjà enregistré"
Pourquoi RPC : RLS UPDATE sur inscriptions_stages exige is_admin() → PATCH direct via clé anon échoue silencieusement (0 lignes). SECURITY DEFINER + HMAC = bypass contrôlé.
